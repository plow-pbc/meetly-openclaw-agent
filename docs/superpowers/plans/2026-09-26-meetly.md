# Meetly Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This plan gives specifications and rules, not code: write the code yourself, test-first, to the contracts below.

**Goal:** Build Meetly, an OpenClaw agent image on Plow that books meetings for its owner: every 5 minutes it reads the owner's new iMessages through Latch, opens a Plow group with whoever wants to meet, offers and holds free times from the owner's Google Calendar, books the one picked, and tells the owner afterwards. The owner can also ask it in their DM to set something up with someone.

**Architecture:** A *variant* of the Plow OpenClaw base image (`FROM base@digest` + prompt + skills). No fork of `boot/` or `plugin/`. The LLM does the work in agent turns: OpenClaw's native cron fires an isolated agent turn every 5 minutes, the way The Founder Times does. Deterministic pieces (state files, cron registration, calendar math) are small TypeScript CLIs under `skills/meetly/scripts/`, run by the agent with `exec` as `node <script>.ts`, with no build step.

**Tech Stack:** TypeScript (erasable syntax only) run directly by Node ≥ 24.16; `node:test` + `node:assert/strict`; `tsc --noEmit` for typecheck; Docker; OpenClaw 2026.9.6 (from the base image); Latch skills on the owner's Mac (`plow-messages`, `contacts`, `google-workspace`/`plow-gog`).

**Spec:** `docs/superpowers/specs/2026-09-26-meetly-design.md`. It is the source of truth for behaviour; this plan turns it into tasks. If the two disagree, the spec wins, so stop and ask.

## Git workflow (one PR per task)

For each task, in order:

1. `git checkout main && git pull`, then `git checkout -b task/<NN>-<slug>` (e.g. `task/01-scaffold-store`).
2. Implement test-first; `npm run typecheck` and `npm test` pass locally.
3. Commit with the task's conventional commit message (English). Extra commits on the branch are fine; each one is conventional.
4. `git push -u origin <branch>`, then `gh pr create --base main` with the title equal to the commit message and a body containing: what the task delivers, the tests added, how it was verified, anything deferred to [LOCAL].
5. Wait for the `check` workflow (from Task 1 on). A failure → fix on the same branch and push again. Never merge red.
6. Merge with `gh pr merge --squash --delete-branch`; the squash title is the conventional commit message.
7. Only then start the next task from the updated `main`.

Never push to `main` directly. Never force-push `main`. If a task cannot be finished, leave its PR open as a draft, say why in the PR, and stop.

## Global Constraints

- Node `>=24.16`; scripts run as `node /opt/plow/skills/meetly/scripts/<name>.ts` with no build, transpile or bundler.
- TypeScript erasable syntax only: no `enum`, `namespace`, parameter properties, decorators. Relative imports carry the `.ts` extension. `tsconfig`: `strict`, `noEmit`, `allowImportingTsExtensions`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `module`/`moduleResolution` `nodenext`.
- No runtime dependencies. Dev dependencies only: `typescript` and `@types/node` (pin the versions the base uses: `typescript 6.0.3`, `@types/node 26.6.2`).
- Every CLI prints exactly one JSON line on stdout on success. On failure it writes `error: <message>` to stderr and exits non-zero. Never print partial results on failure.
- Every CLI keeps its logic in exported pure functions; the CLI wrapper only parses args, reads/writes state and prints. `now`, `fetch` and the process runner are injectable.
- State dir: `MEETLY_HOME` env, default `/var/lib/plow/meetly`. All writes are atomic (temp file + rename, mode 0600). Every read-modify-write takes the file lock.
- Names: agent `Meetly`; `AGENT_ID=meetly`; cron jobs and skills prefixed `meetly-`. Never touch a cron job without that prefix.
- Voice: every message to anyone but the owner is written by Meetly about the owner in the third person, using `ownerName` ("Jean is free Tue 29/9 12:00"), in the other person's language. Never first person as the owner, never signed as the owner.
- Only the defaults the spec fixes: minimum notice 120 min, slot step 30 min, 3 slots per offer, holds expire after 48 h (`MEETLY_HOLD_HOURS` overrides, for testing only).
- Commits: conventional commit messages (`feat:`, `test:`, `chore:`, `docs:`), one squash-merged PR per task (see Git workflow). `docs/` is git-ignored and never committed; reviewer and spike records go in `checks/`.
- Tests: `npm test` runs `node --test "tests/**/*.test.ts"`; `npm run typecheck` runs `tsc --noEmit`. Both must pass at the end of every task.

## Review Focus

The inputs and failure modes below are the ones most likely to hurt a real owner. Each one gets its own test in the owning task:

1. **The same person written two ways.** iMessage gives `+15551234567` and Contacts gives `(555) 123-4567`: the ledger must treat them as one person, or the owner gets two groups (Task 6).
2. **Setup answers in natural form.** A window like `9-18`, `9h-18h`, `09:00–18:00` (en dash) or `9:30 to 17` must be accepted, and `18-9` rejected (Task 4).
3. **A corrupt state file fails loudly.** A `ledger.json` or `cursor.json` that is not valid JSON must make the CLI fail, and must never be silently reset to empty: a reset re-reads all history or loses the holds (Task 1).
4. **A multi-day all-day busy event** (vacation) blocks every day it spans, in the owner's zone (Task 7).
5. **A date-range restriction** such as "next week" (`--from`/`--to`) combined with a horizon longer than the range returns only slots inside the range (Task 8).

## Task 1: Repository scaffold, CLI helpers and the state store

**Files:** create `package.json`, `tsconfig.json`, `.github/workflows/check.yml`, `skills/meetly/scripts/{cli,paths,store}.ts`, `tests/helpers.ts`, `tests/store.test.ts`.

**Interfaces produced:**
- `paths.ts`: `home(): string` reads `MEETLY_HOME` **at call time** (default `/var/lib/plow/meetly`); `file(name: string): string`.
- `cli.ts`: `isMain(importMetaUrl: string): boolean` (true when this module is the `node` entry, comparing against `pathToFileURL(resolve(process.argv[1]))`); `run(fn: () => unknown | Promise<unknown>): void`, which prints `JSON.stringify(result)` plus a newline when the result is not `undefined`, and on a throw prints `error: <message>` to stderr and sets `process.exitCode = 1`; `readInput(paths?: string[]): string[]`, which reads the given files, or stdin when none.
- `store.ts`:
  - `readJson<T>(path, fallback: T): T`: returns `fallback` **only** on ENOENT. Invalid JSON throws an error whose message includes the path, and the file is left untouched.
  - `writeJson(path, value)`: `mkdir -p` the directory, write a temp file in the same directory, `rename` it over the target, mode 0600.
  - `withLock<R>(path, fn, opts?)`: lock is `mkdir <path>.lock`. On EEXIST it retries every 100 ms until `waitMs` (default 10 000), then throws `lock busy: <lock>`. A lock whose mtime is older than `staleMs` (default 60 000) is removed and retried. The lock is always released in `finally`. `opts` accepts `now` and `sleep` for tests. The sleep is synchronous: use `Atomics.wait` on a `SharedArrayBuffer`.
  - `updateJson<T>(path, fallback, fn: (v: T) => T): T`: `withLock` + `readJson` + `writeJson`, returning the new value.
- `tests/helpers.ts`: `tmpHome()` (a fresh `mkdtemp` dir); `cli(script, args, env, input?)` spawns `process.execPath` on `skills/meetly/scripts/<script>` with `env` merged into `process.env` and returns `{ status, stdout, stderr, json }`, where `json` is the parsed stdout or `undefined`.

**Tests (`store.test.ts`):**
- missing file → fallback
- corrupt JSON → throws, with the path in the message, and the file content is unchanged *(Review Focus 3)*
- write/read round-trip, and no `*.tmp` left in the directory
- `updateJson` applies the change and leaves no `.lock` directory
- a held lock plus injected clock and sleep → throws `lock busy` after `waitMs`
- a lock dir with mtime 2 min old → broken, and `fn` runs

**Done when:** `npm install && npm run typecheck && npm test` pass. Commit: `chore: scaffold meetly agent with state store`.

## Task 2: Time-zone helpers

**Files:** create `skills/meetly/scripts/time.ts`, `tests/time.test.ts`.

**Interfaces produced** (all times are epoch ms, all zones IANA):
- `type Day = "mon"|"tue"|"wed"|"thu"|"fri"|"sat"|"sun"` and `DAYS: readonly Day[]` in that order. Export them from here; `config.ts` re-exports them.
- `wallParts(ms, tz) → { y, m, d, hh, mm, ss, weekday: Day }`, via `Intl.DateTimeFormat("en-US", { timeZone, hourCycle: "h23", … })`.
- `offsetMs(ms, tz) → number`: the zone offset at that instant.
- `zonedToUtc(y, m, d, hh, mm, tz) → ms`: guess `Date.UTC(...)`, subtract the offset, then recompute the offset at the result once (correct across DST).
- `localIso(ms, tz) → "YYYY-MM-DDTHH:MM:SS±HH:MM"`.
- `addDays(y, m, d, n) → { y, m, d }`: calendar arithmetic via `Date.UTC`.

**Tests:**
- `America/Sao_Paulo`: 2026-09-28 10:00 local = `13:00Z`, and `localIso` round-trips.
- `America/Los_Angeles`: 2026-10-31 09:00 = `16:00Z` (PDT) and 2026-11-01 09:00 = `17:00Z` (PST; DST ends that day).
- `wallParts(...).weekday` is `mon` for 2026-09-28.
- `addDays` across a month end.

Commit: `feat: add time zone helpers`.

## Task 3: Cron registration (port of `register_crons.py` / `cron_backend.py`)

**Files:** create `skills/meetly/scripts/cron-backend.ts`, `skills/meetly/scripts/register-crons.ts`, `tests/register-crons.test.ts`.

**Interfaces produced:**
- `cron-backend.ts`:
  - `type Proc = { status: number; stdout: string; stderr: string }`, `type Runner = (argv: string[]) => Proc`; `spawnRunner` uses `spawnSync` with a 120 s timeout.
  - `type CronJob = { id: string; name: string; enabled?: boolean; sessionTarget?: string; schedule?: { kind?: string; everyMs?: number }; payload?: { kind?: string; message?: string; timeoutSeconds?: number } }`.
  - `type JobSpec = { name: string; every: string; everyMs: number; timeoutSeconds: number; message: string }`.
  - `cronBackend(runner = spawnRunner, base = ["node", "/app/openclaw.mjs"])` returns `{ list(): CronJob[]; create(spec, enabled: boolean); edit(id, spec); setEnabled(id, enabled); remove(id) }`.
    - `list` runs `cron list --all --json` and **throws** (message starting `refusing to touch the scheduler:`) on: non-zero exit, stdout that is not JSON, `jobs` that is not an array of objects with string `id` and `name`, or `hasMore: true`. It never treats "could not read" as "nothing registered".
    - `create`: `cron add --name --every --session isolated --message --timeout-seconds --no-deliver [--disabled] --json`. **No `--model`**, so the job inherits the base default.
    - `edit`: `cron edit <id> --every --session isolated --message --timeout-seconds --no-deliver`.
    - `setEnabled`: `cron edit <id> --enable|--disable`.
    - `remove`: `cron rm <id> --json`.
    - Any non-zero exit throws with stdout and stderr in the message.
- `register-crons.ts`:
  - `POLL_MESSAGE` is exactly `"Meetly poll. Load the meetly-poll skill and follow it exactly."`. The prompt in Task 10 keys on the prefix `Meetly poll.`.
  - `SPEC: JobSpec[]` = one job `{ name: "meetly-poll", every: "5m", everyMs: 300000, timeoutSeconds: 600, message: POLL_MESSAGE }`.
  - `type Action = { op: "create"|"edit"|"enable"|"disable"|"remove"; name: string; id?: string }`.
  - `plan(jobs, spec, paused): Action[]` (pure):
    - only jobs whose name starts with `meetly-` are considered
    - missing → `create`
    - drift → `edit`. Drift is judged **only on fields the scheduler reported**: `schedule.kind` not `every`, `everyMs`, `payload.message`, `payload.timeoutSeconds`, `sessionTarget` not `isolated`. A missing field is not drift.
    - enabled state ≠ `!paused` → `enable`/`disable`
    - duplicates of a spec name → `remove` all but the first
    - `meetly-*` not in spec → `remove`
    - never remove-then-create
  - `reconcile(backend, paused, spec = SPEC): Action[]` executes the plan; a create while paused passes `enabled=false`.
  - `registerFromConfig(backend = cronBackend(), set?: { paused: boolean })` reads `config.json`; throws `setup is not finished` when `setupDoneAt` is missing (checked **before** writing anything); with `set`, writes `paused` into `config.json` under the lock; then reconciles. Returns `{ paused, actions }`.
  - CLI: `register-crons.ts [--pause | --resume]`. Passing both is an error.

**Tests:** use a stateful fake runner that interprets `list/add/edit/rm` argv over an in-memory job list.
- `plan`: empty → create; exact match → `[]`; message drift → edit; paused plus enabled → disable; a foreign job like `heartbeat` is ignored; orphan `meetly-old` → remove; duplicate `meetly-poll` → remove one.
- `list` refuses on: non-zero exit, non-JSON, bad shape, `hasMore`.
- The `create` argv has `--every 5m --session isolated --no-deliver` and no `--model`.
- `registerFromConfig`: the first run creates; a second run returns `[]` (idempotent); `--pause` sets `config.paused` and disables; `--resume` re-enables; refuses before setup.

Commit: `feat: register meetly cron jobs idempotently`.

## Task 4: Config and owner setup

**Files:** create `skills/meetly/scripts/{config,setup-status,record-setup}.ts`, `tests/setup.test.ts`.

**Interfaces produced:**
- `config.ts`:
  - `type Calendar = { account: string; id: string }`.
  - `type Config = { ownerName; timezone; days: Day[]; windowStart: "HH:MM"; windowEnd: "HH:MM"; durationMin; horizonDays; calendars: Calendar[]; defaultAccount; setupDoneAt?; paused? }`.
  - `FIELDS = ["ownerName","timezone","days","window","durationMin","horizonDays","calendars"]` (this order is the question order) and `type Field`.
  - `QUESTIONS: Record<Field, string>`, short English questions (the agent translates):
    - ownerName: "What name should I use for you when I talk to other people?"
    - timezone: "What time zone are you in?"
    - days: "Which days of the week can I book meetings for you?"
    - window: "Between what times on those days?"
    - durationMin: "How long should a meeting be by default, in minutes?"
    - horizonDays: "How many days ahead can I offer times?"
    - calendars: "Which of your calendars should count as busy?"
  - Constants `MIN_NOTICE_MIN = 120`, `STEP_MIN = 30`, `SLOT_COUNT = 3`; `holdHours()` returns `MEETLY_HOLD_HOURS` when it is a positive number, otherwise `48`.
  - `parseTime(raw) → "HH:MM"`: accepts `9`, `9h`, `9:30`, `9h30`, `09:00`.
  - `minutes("HH:MM") → number`.
  - `parseField(field, value) → Partial<Config>`, which throws a human-readable message on invalid input:
    - `ownerName`: 1–60 characters.
    - `timezone`: must construct an `Intl.DateTimeFormat`, otherwise `unknown time zone: X`.
    - `days`: split on commas/spaces, first 3 letters lowercased, each must be in `DAYS`, de-duplicated, kept in week order, not empty.
    - `window`: split on `-`, `–`, `—`, `to`, `até`, `a` (surrounded by spaces or not), exactly two times, start < end → `windowStart`/`windowEnd`.
    - `durationMin`: integer 15–240.
    - `horizonDays`: integer 1–30.
    - `calendars`: JSON `{ "defaultAccount": string, "calendars": [{ "account", "id" }] }`, non-empty strings; `{ account: defaultAccount, id: "primary" }` is appended when absent (holds live there).
  - `validateConfig(partial) → Config` requires every field and `durationMin ≤ window length`, and carries over `setupDoneAt`/`paused` when present.
  - `nextField(draft) → Field | undefined`.
  - `loadConfig() → Config` throws `Meetly is not set up yet` unless `config.json` has `setupDoneAt`.
- `setup-status.ts`: `status(now = Date.now())`:
  - Done → `{ status: "READY", config, range: { from: localIso(now), to: localIso(now + (horizonDays + 1) days) } }`. The `range` is what the skills pass to `plow-gog calendar events`.
  - Otherwise → `{ status: "SETUP_NEEDED", next: Field | null, question: string | null, draft }`, where the draft lives in `config.draft.json`.
- `record-setup.ts`:
  - `record(field, value)`: unknown field → error.
    - After setup: merge into `config.json` through `validateConfig` under the lock, and return `{ saved, config }`.
    - Before setup: merge into `config.draft.json`, and return `{ saved, next, question }`.
  - `finish(register: () => unknown, now)`:
    - With a draft: `validateConfig(draft)` plus `setupDoneAt`, write `config.json`, delete the draft, and return `{ done: true, config, crons: register() }`.
    - If already done and there is no draft: re-run `register()` only.
    - When `register` throws, `config.json` stays written and the error propagates (the owner can re-run `--done`).
  - CLI: `--field F --value V` or `--done`. The CLI's `register` is `() => registerFromConfig()`.

**Tests:**
- empty home → `SETUP_NEEDED`, next `ownerName`
- recording all seven fields in order → `next: null`
- `days "Mon, Tue ,wed"` → `["mon","tue","wed"]`
- window variants `9-18`, `9h-18h`, `09:00–18:00`, `9:30 to 17` → correct values; `18-9` → error *(Review Focus 2)*
- invalid timezone via CLI → exit 1, stderr contains `unknown time zone`
- `durationMin` `5` and `abc` rejected
- `calendars` appends the default `primary`
- a duration longer than the window is rejected
- `finish` with a fake register: `config.json` has `setupDoneAt`, the draft is gone, register called once
- after setup, `record window` updates `config.json` and keeps `setupDoneAt`
- `READY` includes `range.from`/`range.to` in the owner's zone

Commit: `feat: add owner setup and config`.

## Task 5: Message cursor

**Files:** create `skills/meetly/scripts/cursor.ts`, `tests/cursor.test.ts`.

**Interfaces produced:**
- `type Cursor = { rowid: number | null; updatedAt?; failingSince?; warnedAt? }`, default `{ rowid: null }` in `cursor.json`.
- `WARN_AFTER_MS = 30 * 60_000`.
- `setRowid(c, rowid, now)`:
  - integer ≥ 0 only
  - **refuses to move backwards** (`cursor never moves back`)
  - clears `failingSince`/`warnedAt`
- `markFail(c, now) → { cursor, warn }`:
